# Модуль 6. Поведение серверного аудита

В МоемСкладе есть внутренний Audit Log (системный журнал аудита, куда записываются действия пользователей компании).

В ходе практического теста было выяснено, на какие действия кассы сервер создает записи:

## 1. Чтение данных (GET) и ошибки доступа (403)

- Одиночный GET-запрос настроек кассы (`/settings/retailstore`).
- Опрос списка чеков и суммы налички.
- Попытка запросить данные чужой точки продаж с получением отказа `HTTP 403 Forbidden` (ошибка 12013).
- **Результат в журнале:** 0 записей. Чтение данных сервером в аудит не записывается.

## 2. Перепривязка кассы (POST /admin/attach)

Когда в кассе вводят логин и пароль и выбирают точку продаж через вызов `POST /api/posap/1.0/admin/attach/{id}`, сервер выпускает новый ключ и фиксирует событие:

```json
{
  "source": "posapi",                                           // Источник действия: кассовый API
  "eventType": "replacetoken",                                  // Тип события: смена токена кассы
  "entityType": "retailstore",                                  // Тип объекта: точка продаж
  "name": "Точка 1",                                            // Название точки продаж
  "info": {
    "additionalInfo": "(IP-адрес, User-Agent)"                  // Сетевой IP-адрес и отпечаток браузера
  }
}
```

## Практический вывод по аудиту

1. Серверный аудит настроен на отслеживание мутаций (изменений данных, удалений и создания документов) и перевыпуска ключей (`replacetoken`).
2. Обычное чтение баланса кассы, чеков и остатков по уже существующему токену расценивается сервером как штатный пинг связи работающей кассы и не оставляет следов в журнале безопасности.
